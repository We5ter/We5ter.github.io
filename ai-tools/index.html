控制面与数据面拆得很干净：控制器只管生命周期，HTTP 走 sandbox-router（X-Sandbox-* 头契约），进程执行走 sandboxd 的 gRPC。休眠不是 checkpoint——置 Suspended 只删 Pod、留住 PVC，唤醒重挂同一块盘，内存态必丢。热池申领是「改归属」不是「建 Pod」，ownerRef 一换就到手，所以能压到百毫秒；但 claim 里写了 env 或 volumeClaimTemplates 会静默退化成冷启动。默认值偏保守：不挂 ServiceAccount token、NetworkPolicy 封 RFC1918 和 metadata。短板在时间——自动挂起/按流量唤醒、scale-to-zero、模板滚动更新、MCP server、TS SDK 全挂在 roadmap，API 还是 v1beta1 且不承诺兼容。 The control and data planes are cleanly split: the controller only owns lifecycle, HTTP goes through sandbox-router (the X-Sandbox-* header contract), process execution through sandboxd's gRPC. Hibernation is not a checkpoint — setting Suspended deletes the Pod and keeps the PVC, so the wake reattaches the same disk and loses all memory state. Claiming from a warm pool is an ownership reassignment, not a Pod creation — one ownerRef swap, hence sub-second claims; but putting env or volumeClaimTemplates in the claim silently degrades it to a cold start. Defaults are conservative: no ServiceAccount token, NetworkPolicy blocks RFC1918 and the metadata endpoint. The weak point is time — auto-suspend, traffic-triggered resume, scale-to-zero, template rollouts, the MCP server and the TS SDK are all still roadmap, the API is still v1beta1, and compatibility isn't promised.
